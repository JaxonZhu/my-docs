# RoboDojo 论文解读：统一仿真与真机的机器人操作评测

论文原题：RoboDojo: A Unified Sim-and-Real Benchmark for Comprehensive Evaluation of Generalist Robot Manipulation Policies

- 作者：Tianxing Chen、Yue Chen、Zixuan Li 等
- 机构：香港大学、加州大学伯克利分校、清华大学、北京大学等多所高校与研究团队
- 发表：arXiv，2026 年 7 月 5 日首次提交
- 论文：[arXiv:2607.04434](https://arxiv.org/abs/2607.04434)
- 项目：[RoboDojo 官方项目页](https://robodojo-benchmark.com/)
- 代码：[RoboDojo-Benchmark/RoboDojo](https://github.com/RoboDojo-Benchmark/RoboDojo)
- 排行榜：[RoboDojo Leaderboard](https://robodojo-benchmark.com/leaderboard)

RoboDojo 将可规模化的仿真评测与标准化真机测试放进同一套策略接入流程：仿真侧用 42 个任务检查五类能力，真机侧用三种机器人上的 18 个任务暴露物理部署问题，XPolicyLab 则统一模型的数据转换、策略接口和部署通信。

我阅读这份报告时，最关注的是标准化如何落地：任务与随机化怎样配置，真实场景如何复位，成功率与部分进展怎样评分，以及一个策略如何在仿真和真机之间复用接口。

:::{note}
**阅读版本**：正文的方法、数据与实验分析依据保存的 2026 年 7 月 1 日技术报告及原始笔记整理。该报告标题使用 *Efficient Evaluation*，当前 arXiv 标题使用 *Comprehensive Evaluation*。下文的模型结果属于所附报告中的固定实验记录，不代表实时排行榜；接口说明也按报告描述，未进行当前训练代码复核。
:::

## 一、为什么需要仿真与真机共同评测？

### 1.1 任务数量不等于能力覆盖

作者指出，一些 benchmark 虽然包含很多任务，但底层操作模式仍可能集中在短程 pick-and-place。改变物体、摆放位置或语言表达可以测试一定程度的泛化，却未必充分覆盖记忆、精细接触、子任务切换和开放语义理解。

RoboDojo 因此按能力维度组织任务，希望回答的不只是“总共完成了多少”，还包括“模型究竟在哪类能力上失效”。

### 1.2 两种评测环境各有作用

仿真便于并行执行、重复试验和控制随机因素，适合模型迭代与能力诊断；真机可以暴露接触动力学、感知噪声、执行延迟、标定误差和动作不稳定等问题，但依赖硬件布置、人工复位与一致的评分协议。

**我的理解**：统一评测的价值，是让同一个模型接入方式能够支持两类互补证据。仿真分数不能替代真机可靠性，真机的小规模测试也难以独自承担广泛的能力诊断。

### 1.3 三个组件各自负责什么？

| 组件 | 主要职责 |
| --- | --- |
| Simulation Benchmark | 42 个任务、五类能力；基于 Isaac Sim / Isaac Lab 进行异构并行评测 |
| RoboDojo-RealEval | 18 个真机任务、三种本体；标准化硬件、照明、场景复位、执行与评分 |
| XPolicyLab | 统一数据转换、策略接口和服务协议，让不同架构接入同一评测流程 |

:::{important}
**统一评测流程不等于成对的 sim-to-real 测试**。RoboDojo 没有为所有仿真任务构建一一对应的真机任务，也不以匹配任务上的直接迁移成功率为目标。仿真与真机任务集互为补充，结果不能直接解释成某个模型的 sim-to-real 保真度。（来源：报告 §3.2.1）
:::

## 二、仿真任务如何覆盖五类能力？

```{figure} images/RoboDojo/robodojo-tasks.png
:alt: RoboDojo 的 42 个仿真任务按五个维度分组，18 个真机任务按三种机器人本体分组
:width: 100%
:align: center

**原报告图 2：任务总览**。上半部分按能力组织仿真任务，下半部分展示三个真机平台的任务。DLC 是额外训练数据，不计入 42 个评测任务。
```

| 维度 | 任务数 | 主要考察的能力 |
| --- | ---: | --- |
| Generalization | 12 | 对背景、光照、杂物和目标物体变化的鲁棒性 |
| Memory | 6 | 历史观测、关键帧记忆与当前画面不足以决定动作时的推理 |
| Long-Horizon | 8 | 维持任务进度、完成多个子步骤并处理中间错误 |
| Precision | 8 | 精确定位、平滑运动与接触过程中的控制稳定性 |
| Open | 8 | 理解未见任务要求，重组已学技能并将语言目标落到动作上 |

### 2.1 Generalization 与 Open 的区别

Generalization 主要改变已经定义好的任务中的视觉与场景条件。例如，策略需要在不同背景、光照或干扰物布局下继续完成操作。训练示范在标准配置中采集，评测再引入随机化条件。

Open 则改变任务要求。所需原子技能可能在其他训练任务中出现过，但具体目标或技能组合未在该任务的示范中直接提供。例如，`general_pickup` 使用训练中常见的抓取技能，却要求根据新的目标描述完成抓取。

因此，Open 没有对应的任务专属训练轨迹，并不表示策略训练时完全没见过相关动作；它要测试的是技能重组与语义迁移。（来源：报告 §3.1.1–3.1.2）

### 2.2 Memory 与 Long-Horizon 也不是同一个问题

Memory 要求模型使用当前观测中已经消失的信息，例如先前出现的目标、顺序或关键线索。仅看当前帧可能无法决定正确动作。

Long-Horizon 则要求持续执行任务结构：知道已经完成哪些步骤、下一步做什么、何时切换，以及中间失败后如何继续。保存了历史观测，不代表就能正确调度后续动作。

### 2.3 Precision 关注局部闭环控制

Precision 不只是理解目标位置，还要求在小容差下稳定执行。例如，`insert_tubes` 要将管状物连续插入狭窄孔位，微小定位误差、动作抖动或接触后的修正不足都可能导致失败。

这类任务把“知道要做什么”和“能否准确做成”区分开来，也使最终成功率对底层控制质量更加敏感。

## 三、仿真平台与数据如何构建？

### 3.1 YAML 配置与受控的场景初始化

RoboDojo 使用 Isaac Sim 与 Isaac Lab，将任务描述和仿真运行分离。模块化 YAML 规范包含任务资产、布局、初始化分布、随机化范围和成功条件；共享运行框架根据配置实例化具体任务。

在 reset 时，平台在随机种子控制下采样目标对象、对象位姿、关节状态、杂物布局、光照和背景纹理。固定配置与种子，使场景变化可以被复现和比较。（来源：报告 §4.1.1；附录 E.1）

**我的理解**：标准化的重点不是让每个 episode 看起来相同，而是明确哪些因素允许变化、按什么分布变化，以及如何重现这次变化。种子控制也不等于不同硬件上的仿真逐位确定，报告仍通过跨 GPU 实验测量残余波动。

### 3.2 资产需要同时具备视觉、物理与任务信息

平台包含刚性、铰接和可变形资产。刚性物体来自公开资源及使用 Meshy AI 重建的日常物体；铰接和可变形资产来自开源平台、3D 扫描，以及 ClothesNet 中选取的衣物模型。

这些资产进入任务前，还需要整理碰撞几何、运动学结构、材料参数与仿真表示：

- **刚性物体**需要碰撞形状与物理参数。
- **铰接物体**需要关节配置、关节限位和初始关节状态。
- **可变形物体**需要适合形变仿真的网格与材料参数。

资产还附带对象类别、语言描述、可放置区域、可操作部位及成功检查等元数据。它们既支持任务构造，也为自动生成演示提供抓取区域和交互点。（来源：报告 §4.1.2；附录 E.2）

:::{note}
**为什么衣物资产不能只看外观？** 衣服的静态网格即使视觉上逼真，也未必适合大形变与接触仿真。原笔记对 ClothesNet 的关注点在于这一差别：用于机器人操作的数据，还需要支持抓取点、边界和可变形行为。RoboDojo 使用了其中的部分资产，并对进入平台的物理表示做标准化。
:::

### 3.3 异构并行执行

普通矢量化仿真常复制相同场景模板，只改变位姿或随机种子。RoboDojo 支持各并行环境拥有不同的对象类别、资产几何、干扰物数量、铰接结构和任务布局，同时通过共享的矢量化接口推进仿真。

更大规模运行时，系统将 episodes 和 seeds 分配到多个 GPU，启动独立仿真进程，每个进程执行一部分任务与种子，最后汇总结果。这里的“异构”强调并行场景本身可以不同，而非只是在一批相同桌面上重复执行。（来源：报告 §4.1.3；附录 E.3）

### 3.4 自动轨迹合成与 VR 遥操作

平台提供两种演示采集方式：

1. **自动合成**：将 `grasp`、`place`、`handover`、`insert`、`open`、`close`、`stack` 等低层技能组合起来，利用资产注释确定交互位置，由 cuRobo v2 生成运动。
2. **VR 遥操作**：通过 Meta Quest、Pico 等设备采集控制器的增量 6D 位姿，映射为末端执行器目标，再由运动生成模块求解机器人运动。

报告给出的单个 6-DoF ARX X5 机械臂示例中，每个规划步骤的求解延迟约为 3 ms。这是特定设置下的运动求解延迟，不能当作完整策略推理或端到端机器人响应时间。（来源：报告 §4.1.4；附录 E.4）

cuRobo 在这里承担从运动目标到可执行轨迹的计算，服务于演示合成与遥操作。它与后面评估的 VLA 策略属于不同层次，不能将规划器的效率直接归为策略本身的能力。

### 3.5 训练数据规模与 DLC 的作用

仿真训练包含 34 个任务，每个任务 100 条轨迹，再加一个包含 100 条轨迹的辅助 DLC 数据目录：

```{math}
N_{\mathrm{train}} = 34\times100+100=3500.
```

因此是 **35 个训练数据目录、3,500 条轨迹**，而非 35 个 benchmark 评测任务。数据以 25 Hz 记录，共 1,859,602 帧、约 20.66 小时。8 个 Open 任务不提供任务专属训练示范。

```{figure} images/RoboDojo/robodojo-sim-data.png
:alt: 仿真数据按 Generalization、Memory、Precision、Long-Horizon、Open 和 DLC 统计帧数、时长与轨迹数
:width: 100%
:align: center

**原报告表 7：仿真训练数据统计**。Open 仅用于评测；其他四类任务各提供每任务 100 条演示，DLC 额外提供 100 条随机化轨迹。
```

Generalization 的任务训练示范使用标准视觉设置。额外 DLC 轨迹在背景、光照、杂物布局等复杂随机化条件下采集，用于扩大训练中的视觉分布，减轻对默认桌面与固定场景的依赖。它是独立的辅助数据，不能理解成每个 Generalization 任务都额外增加 100 条随机化示范。

**我的疑问**：各任务虽然轨迹数相同，但不同维度的任务数、帧数与时长并不相同。Generalization 和 Long-Horizon 的总时长较多，可能影响模型在不同能力上的学习机会。若要进一步分析“哪种能力更难”，可以另做控制训练帧数或时长的实验；仅凭当前分布，不能断言维度间差距由数据量造成。

## 四、仿真评测与总分怎样计算？

### 4.1 区分训练任务、评测任务与随机种子

每个评测任务运行 50 个 episodes，覆盖全部 42 个任务：

```{math}
N_{\mathrm{eval,\,per\ seed}}=42\times50=2100.
```

34 个训练任务之外，8 个 Open 任务也参加评测。大部分策略训练三个随机种子，因此每个任务累计 150 次，每个策略合计 6,300 次仿真 rollout；报告说明部分模型存在例外，不能把三 seed 当作所有条目都满足的条件。（来源：报告 §3.1.3、§5.1）

Generalization 的 50 次评测进一步分成 **25 次标准场景**与 **25 次随机化场景**，检查 in-domain 表现和场景分布变化下的鲁棒性。

### 4.2 成功率与部分进展分数分别报告

- **Success rate** 判断任务是否最终完成。
- **Score** 反映中间子步骤或部分任务进展。

模型能完成前几个步骤，却在最后的对齐、接触或状态切换上失败时，可能得到部分分数，但不会被计作最终成功。

仿真总体指标按五个能力维度**等权平均**。用 $M_d$ 表示第 $d$ 个维度的成功率或 score，则汇总形式为：

```{math}
M_{\mathrm{overall}}=\frac{1}{5}\sum_{d=1}^{5}M_d.
```

这不是直接对全部 42 个任务等权平均，目的在于避免含有更多任务的维度在总分中占据更大权重。它平衡的是评测汇总权重，并没有自动平衡前述训练数据时长。

### 4.3 执行时限也属于评测条件

仿真任务的最大交互 horizon 按任务示范长度的第 90 百分位数设定，通常乘以 1.2；自动合成的短任务使用 1.5 倍，以免小幅时长变化导致过早终止。真机采用的 1.5 倍规则另见后文，不能把所有设置统称为同一个系数。（来源：附录 C.2）

## 五、RoboDojo-RealEval 如何实现真机标准化？

### 5.1 三种本体与固定硬件几何

真机 benchmark 使用 **ARX X5、Piper、Piper X** 三种双臂平台，每种本体 6 个任务，共 18 个任务。不同平台带来不同的运动学、工作空间和相机视角；每种本体对应的任务也不同。

```{figure} images/RoboDojo/robodojo-hardware.png
:alt: RoboDojo-RealEval 的标准化真机平台、相机、光照和操作界面
:width: 100%
:align: center

**原报告图 6：RoboDojo-RealEval 平台**。硬件结构与操作界面共同固定传感器、机器人和工作区关系，支持场景复位、策略执行与记录。
```

主要硬件约束包括：

- 固定高度的白色桌面，工作区为 **1.2 m × 1.2 m**；外部框架为 **1.5 m × 1.5 m × 2.1 m**。
- 左、右、正面和顶部使用黑色遮光帘，三个固定安装的线性 LED 光源提供照明。
- 连接件固定双臂之间的相对位置与方向，支架固定头部相机位姿。
- 使用两台 **Gemini 305 腕部相机**和一台 **Gemini 335L 头部相机**，提供局部操作视角与全局工作区视角。
- 触摸屏 Web 界面用于复位、运行策略、停止执行、录制和评分相关操作。

这里的标准化覆盖了物理几何与视觉条件，而不只是给所有模型发送相同形状的观测张量。（来源：报告 §4.2；附录 F、F.1）

### 5.2 布局重放由图像叠加辅助人工完成

每次 trial 前，系统将预先记录的目标布局图像以透明方式叠加在实时相机画面上。评估者对照两者调整物体位置，恢复规定的初始布局。

“重放布局”不是播放旧视频作为模型输入，也不是系统自动把物体全部摆回原位。它是用图像参考帮助人工复位，从而降低不同策略和不同评测 session 之间的初始条件差异。

报告在 **5 名采集人员、5 个物体的场景**上测得平均复位时间为 **14 秒**。这一结果有具体测试条件，不能推广为所有 18 个任务都固定需要 14 秒。（来源：附录 F）

### 5.3 真机训练数据与质量检查

数据使用同本体的 leader–follower 主从遥操作采集。每个任务由四名操作者合计提供 100 条演示，共 **1,800 条轨迹、1,611,841 帧、约 17.91 小时**，采样率为 25 Hz。

观测包含同步的头部与双腕 RGB 图像、关节状态、末端位姿和语言标注；视频分辨率为 640 × 480。多视角记录和机器人状态使数据能够转换为不同策略所需的训练格式。

```{figure} images/RoboDojo/robodojo-real-data.png
:alt: ARX X5、Piper、Piper X 的真机轨迹数相同，帧数与总时长不同
:width: 100%
:align: center

**原报告表 8：真机演示数据统计**。每种本体 6 个任务、600 条轨迹，但任务结构与执行速度不同，因此帧数和时长并不相等。
```

采集后，人工检查三个方面：试验前平台是否按协议复位，操作者是否存在过度犹豫，以及任务是否成功完成。复位检查包括桌布是否平整、照明是否处于标准强度等条件。该过滤流程针对训练演示质量，不应与后面评测视频的评分流程混为一谈。（来源：报告 §3.2.2；附录 D.1）

### 5.4 试验次数、控制与终止条件

每个真机任务进行 10 次 trials；18 个任务合计 **180 次物理试验／策略**。报告对每个受测策略在每种本体上训练一个 seed，不是直接把仿真的三 seed 设置照搬到真机。

策略输出末端执行器命令时，平台使用 **Pink** 将末端目标转换为机器人关节运动。Pink 基于 Pinocchio 和二次规划实现微分逆运动学，逐步求解关节速度，并结合配置的任务与约束。它属于局部逆运动学方法，不等同于完整的全局避障路径规划。参见 [Pink 官方说明](https://github.com/pink-kinematics/pink)。

真机最大执行步数根据任务示范长度设定：

```{math}
H_{\max}=1.5\times Q_{0.9}(L_{\mathrm{demo}}),
```

其中 $Q_{0.9}$ 为第 90 百分位数。达到步数上限后，trial 结束，机器人回到复位姿态；评估管理员也可因撞桌、碰撞框架或自碰撞等危险行为手动终止。报告描述的紧急停止功能会禁用策略控制，并缓慢返回安全复位状态。（来源：报告 §5.2；附录 D.2、F）

### 5.5 记录与评分

所有 trial 都录制视频，由三名评估者独立评分。报告将其称为双盲协议，附录进一步说明评分者不知道受测策略的身份。评分同时考虑最终成功和中间子步骤，单次 trial 分数取三人平均；报告还描述了处理评分分歧与申诉的机制。

真机总成绩在全部 18 个任务上汇总。由于每种本体任务数相同，也可以分别观察本体内六项任务的平均值，定位模型在不同硬件与任务组合上的差异。

### 5.6 远程评测与官方结果验证

远程接入不必理解成先把模型上传到实验室。报告说明，参与者可以保留远程 policy server，通过统一协议与官方环境客户端通信；私人开发阶段不要求立即公开 checkpoint 或源码。

按该报告描述，正式进入 verified leaderboard 还需满足官方评测、隐藏布局验证、规定的种子或本体覆盖，以及在发布时开放受测 checkpoint、实现、配置、复现说明和评测视频等要求。

公开布局用于主要排行榜测试，隐藏布局用于额外一致性检查，不能把两者颠倒。具体提交规则可能更新，应以[官方排行榜与项目文档入口](https://robodojo-benchmark.com/leaderboard)为准。（来源：报告 §3.3）

## 六、XPolicyLab 如何复用策略接口？

### 6.1 统一外部流程，保留模型内部结构

XPolicyLab 通过共同的数据处理、训练、服务与评测约定接入不同策略。报告实验集成了 30 个代表性模型；这一数量属于报告快照，不是当前仓库支持数量的上限。

原始轨迹可以转换成 HDF5、LeRobot 风格数据、预计算语言 embedding，以及各模型自己的归一化统计。统一 benchmark 数据格式与策略专属训练格式之间，通过适配器衔接。（来源：报告 §4.3；附录 G）

观测格式可以包含语言、多视角图像、机器人状态和元数据。状态字段可涵盖关节位置、末端／TCP 位姿、夹爪状态及移动底盘状态，但这不意味着每个任务或机器人都实际提供全部字段。

位姿采用位置与四元数形式：

```{math}
[x,y,z,q_w,q_x,q_y,q_z].
```

固定字段约定有助于减少适配歧义，仍需结合机器人配置、动作类型和模型归一化处理，才能得到正确的动作含义。

### 6.2 最小策略接口与批量接口

| 阶段 | 单环境接口 | 并行仿真接口 |
| --- | --- | --- |
| 初始化与状态清理 | `reset` | `reset` |
| 更新观测 | `update_obs` | `update_obs_batch` |
| 获取动作或动作 chunk | `get_action` | `get_action_batch` |

环境客户端只依赖这些约定，不必访问策略内部网络。单环境在每个 episode 开始时调用 `reset`，随后重复取得观测、请求并执行动作 chunk。一个 chunk 用完后，更新观测并继续查询动作；episode 结束后，才为下一个 episode 重置策略状态。

批量模式维护活跃环境索引，只对仍在运行的环境更新观测、查询动作并执行。已经结束的环境从活跃集合移除。由此，同一个策略服务可以支持异构并行仿真，也可以服务单个真机环境。（来源：附录 G，Table 9）

### 6.3 服务通信与调试

策略运行在 model server，仿真器或真实机器人运行在 environment client。通信采用 **WebSocket + MessagePack**：前者保持双向连接，后者序列化图像、状态、嵌套字典与动作等数据。

这使模型运行环境与机器人环境解耦，也支持远程部署；但统一接口本身不代表网络延迟、动作坐标系或历史状态管理等问题会自动消失。

报告还描述了离线调试模式：先生成形状正确的观测，检查模型加载、观测解析、动作维度、参数传递和通信，再进入完整仿真或真机评估。

### 6.4 脚本与参数组织

策略包按一致的目录约定提供安装、数据处理、训练、模型服务和评测入口，例如 `install.sh`、`process_data.sh`、`train.sh`、`eval.sh`、`model.py`、`deploy.py` 与 `deploy.yml`。

数据集、任务、checkpoint、机器人配置、动作类型和随机种子等参数贯穿数据处理、训练与评测。这让同一实验更容易检查、重跑和对比。这里记录的是报告中的设计约定，具体接入时仍需对照[当前 RoboDojo 仓库](https://github.com/RoboDojo-Benchmark/RoboDojo)及其 XPolicyLab 依赖。

## 七、实验结果揭示了哪些能力缺口？

### 7.1 先看绝对水平，再看模型排名

报告中的仿真实验评估了 30 个模型，真机实验评估了 10 个提交模型。两张表的模型集合不同，因此不能把未进入真机表的模型当成真机失败案例。

| 评测设置 | 代表结果 | 成功率 | Score |
| --- | --- | ---: | ---: |
| 仿真 | Hy-Embodied-0.5-VLA | 8.80% | 13.07 |
| 仿真 | 专家遥操作 | 76.03% | 80.42 |
| 真机 | $\pi_{0.5}$ | 12.8% | 22.9 |
| 真机 | InternVLA-A1 | 7.2% | 12.0 |
| 真机 | GalaxeaVLA | 4.4% | 9.0 |
| 真机 | 专家遥操作 | 100.0% | 100.0 |

这些数值按报告 Table 1–2 整理，success rate 与 score 是两个不同指标。报告正文将榜单冻结日写为 2026 年 6 月 25 日，真机 Table 2 标题却写为 6 月 15 日；这里不将日期差异合并成一个确定的实时榜单版本。

人类参考也有经验背景：仿真侧邀请三位拥有超过 1,000 小时经验的专家；真机侧专家拥有超过 1,500 小时遥操作经验，且参与过对应数据集的构建或采集。因此它说明任务在该协议下可完成，不应视作未经练习的新操作者水平。（来源：报告 §5.1–5.2）

### 7.2 泛化受益于空间理解，但动作执行仍是瓶颈

Spatial Forcing 在报告的 Generalization 维度达到 9.33% 成功率、14.12 score，作者据此讨论显式 3D grounding 与空间表征对齐的价值。其他较强模型的表现，也提示大规模、多本体预训练可能提供更丰富的视觉与交互经验。

但即使该维度的最好成功率也低于 10%。模型识别目标或理解空间关系，并不自动转化成分布变化下可靠的执行。这些解释来自作者对模型差异和 rollout 的分析，不是单独控制预训练规模或架构因素后的因果消融。

### 7.3 长程执行需要正确的子任务切换

Hy-Embodied-0.5-VLA 在 Long-Horizon 上达到 14.92% 成功率、25.74 score；Spatial Forcing 为 14.58% 和 23.26。相对于其他困难维度，结构化多步骤任务取得了一些进展，但绝对成功率仍低。

仅仅保存历史也不够。策略可能记得先前观测，却无法选择下一子任务、在正确时刻切换，或从中间错误中恢复。作者因此将长程任务的难点归结到技能组合与状态相关的执行，而不是单一的记忆容量。

### 7.4 精细操作暴露出弱状态修正

Precision 的模型顺序与总榜不完全一致，X-VLA 在该维度领先。作者观察到，一些模型即使交接或对齐失败，仍继续执行后续插入动作，像是在跟随熟悉的动作顺序，而没有重新检查下一步的前置条件。

末端与关节空间动作抖动进一步放大了接触任务的不稳定。作者提出需要更平滑的控制先验、接触反馈，以及包含纠正和偏离专家轨迹状态的训练信号。这些是针对失败现象提出的方向，不能当成已经通过本报告实验验证的解决方案。

### 7.5 记忆需要参与动作执行

Memory 维度上，Hy-Embodied-0.5-VLA 的成功率为 12.11%；EventVLA 为 4.78%，X-WAM 为 4.67%。EventVLA 的部分失败被作者归因于下游操作不准确，而非完全忘记历史线索。

X-WAM 的 score 为 6.32，高于 EventVLA 的 4.92，但成功率略低，不能笼统地说 X-WAM 在记忆任务上全面更好。作者认为预测式预训练有助于时间连续性和任务进度建模，却未必能可靠保存、检索已经消失的稀疏证据。

### 7.6 Open 仍接近未解决

按报告 Table 1，Open 维度最高成功率也仅为 1.67%（$\pi_{0.5}$）。正文分析曾将最高值写为 1.58%，与表格存在差异，这里采用表格值。相关原子技能虽然出现在训练中，但模型仍难把新语言目标、物体可操作性与可执行动作组合起来。

**我的理解**：这个结果强调的不是 VLM 是否“能看懂一句话”，而是理解之后能否正确选择、组合并闭环执行技能。语言理解能力与机器人动作能力需要在同一任务中同时成立。

### 7.7 仿真与真机结果只能部分对应

报告真机表中，$\pi_{0.5}$ 领先，InternVLA-A1 和 GalaxeaVLA 的相对位置也高于各自在仿真表中的位置。这表明仿真总体排名不足以直接预测物理部署表现。

不过，Hy-Embodied-0.5-VLA 等模型没有出现在该报告的真机受测名单中，不能用“没有上榜”推断其真机性能下降。两边任务也不是一一配对，因此排名差异同时受到任务集、受测模型集合和部署条件影响。

真机部分还揭示了动作振荡、重复无效动作、接触不稳定与需要人工安全终止的行为。即使策略获得一定中间进展，精确对齐、子步骤过渡和错误恢复仍可能阻止最终成功。（来源：报告 §5.3–5.4）

## 八、评测效率、稳定性与后续方向

### 8.1 真机评测效率有具体测量条件

报告以 $\pi_{0.5}$ 为测试策略，将 policy server 部署在与机器人同一局域网的 RTX 4090 工作站，统计场景摆放、推理和执行在内的完整试验成本。18 个任务、180 次物理试验合计约 **202 分钟，即 3.4 小时**；每项任务的 10 次试验平均约 11.2 分钟。

作者称这些试验没有通过人工中断或提前停止来缩短时间。该结果说明标准化流程在这一设置下的效率，不能直接当作跨公网远程服务、其他模型或其他硬件的固定耗时。（来源：报告 §5.5，Table 3）

### 8.2 可复现性需要测量残余波动

仿真稳定性实验使用三个独立 RTX 4090、固定任务布局，以及三个代表策略。报告给出的能力维度成功率标准差最高为 1.1 个百分点，整体平均成功率标准差最高为 0.5 个百分点。

这为所测试硬件与布局下的评测一致性提供证据，但不等于所有 GPU、所有场景或细小模型差异都能无误区分。标准化降低了评测波动，仍需要记录配置、种子、checkpoint 和执行条件。（来源：报告 §5.6.1，Table 4）

### 8.3 阅读后的关注点

我认为 RoboDojo 最有价值的部分，是将任务设计、训练数据、运行接口、真机复位和评分协议一起纳入评测系统。只发布一组任务名称或一个总成功率，往往不足以解释模型为什么失败，也不足以让其他团队复现比较条件。

这份报告同时提醒我区分三组容易混淆的概念：训练任务与评测任务、部分进展与最终成功、仿真诊断与真机部署。接口统一让比较更容易开展，但公平解释结果仍依赖模型覆盖、训练配置、数据分布与评测预算。

作者讨论的未来扩展包括灵巧操作、人形机器人全身控制、触觉操作和移动操作。这些属于后续方向，尚不应计入当前 42 个仿真任务与 18 个真机任务已经覆盖的能力范围。
